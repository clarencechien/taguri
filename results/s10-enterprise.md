# S10　EnterpriseRAG-Bench（51 萬份企業文件）

日期：2026-11-10。花費約 $13.90（估算；上限 $15）。lock 檔照用，沒有在這個題組上調任何參數。

## 結論

1. **整體表現：比 BM25 好，但和 SAG2＋Jev 有落差。** 不含 EG2 的 N1 整體文件 R@10 是 **74.50**，落在「68 到 75」這一區，離 75 差 0.5 分。比 N0 高 5.51 分（95% 信賴區間 +2.73 到 +8.39）。
2. **EG2 的最終判定：保留。** 語意檢索 125 題，含 EG2 減不含 EG2 的 ΔR@10 是 **+9.60**（+3.20 到 +16.00），下界 > 0 而且點估計 ≥ +5。基本檢索 175 題也 +7.43（+4.00 到 +11.43）。
3. 加了 EG2 之後，這兩個題型（300 題）的 R@10 是 79.00；基本檢索 90.86、語意檢索 62.40，都高於上游紀錄的 SAG2＋Jev（86.86、58.40），但那是不同分段方式下的數字，不能配對。
4. **和 S7c 一致**：EG2 在實體型的多跳題（MuSiQue、2Wiki）上沒有幫助，在中文和「問法與文件用詞不同」的企業文件上有幫助。

## 4. 成本與判斷次數

| 項目 | N1（470 題） | N1＋EG2（300 題） |
|---|---:|---:|
| 每題判斷次數：中位數／第 90 百分位／平均 | 168／195／164.3 | 203／231／198.6 |
| 每題輸入 token | 561,652 | 693,685 |
| 執行時間（L40S，16 題並行） | 8,830 秒 | 5,078 秒（部分判斷有快取） |
| 每題佔用的容器時間 | 18.8 秒 | 約 17 秒（有快取，單獨跑會更高） |

| 失敗的題目 | 0 | 0 |

- **更正（寫 README 時發現）**：這 18.8 秒不是 GPU 在算的時間。16 題並行時每題的經過時間中位數是 309 秒，其中等判官的時間中位數只有 21 秒（這一次有上一次中止時留下的判斷快取）；其餘都花在 CPU 上的詞彙檢索。154 萬段的 SQLite FTS5，每題要做十幾次多詞 OR 查詢和上百次候選詞的詞組頻率查詢，這才是這個規模的瓶頸。含 EG2 的那一組等判官的中位數是 143 秒、每題經過時間 258 秒。容器是照時間計費的，所以花費的數字不變，但「每 100 題美元」在這個題組反映的主要是檢索慢，不是判官貴。
- **每題判斷次數的中位數超過 150 的標示線**（168、203）。段落接近 2,000 字元，每題輸入 token 是 MuSiQue 的 6 倍，每題 GPU 時間是 10 倍。這會直接影響 GB10 上的延遲。
- 判官在這個題組比較弱：金標文件的段落只有 44.5% 被判「是」（1,855 段）；非證據有 4.50% 被判「是」（52,962 段，平均每題 5.1 段）。
- 第一次跑 N1 時，已有證據 8 段加起來 17,776 token，超過 16,384 的 context。加了「已有證據最多 10,000 token」的預算後重跑（`docs/design-decisions.md` 第 13 節）。

這一輪要回答的是，每題的判斷次數和輸入 token 能省多少，各自掉多少分。

- 題目：MuSiQue 的校準半（`calib`，150 題）。這一半本來就是拿來調參數的。test、MultiHop-RAG、EnterpriseRAG 都不碰。
- 基準：lock 檔的定案設定（每輪重判 20 段、擴展 2 輪、每輪取 50 段、證據池最多 8 段）。
- 一次只動一個旋鈕，另外排三個事先決定好的組合：

| 代號 | 改動 |
|---|---|
| rj10、rj5 | 每輪重判的段數 20 → 10、5 |
| r1 | 擴展輪數 2 → 1 |
| K30、K20 | 每輪取的候選段數 50 → 30、20 |
| m5 | 證據池上限 8 → 5（影響每次判斷的長度，不影響次數） |
| rj10＋K30 | 組合 |
| rj10＋K30＋m5 | 組合 |
| r1＋rj10＋K30 | 組合（最省） |

- 每一組報告：每題判斷次數、每題輸入 token、R@5、AE@10，以及相對基準的 ΔR@5 和 95% 信賴區間（配對 bootstrap 10,000 次）。
- **「可用的降配」的定義**：ΔR@5 的信賴區間下界 > −3，而且 ΔAE@10 的點估計 ≥ −4。

## 結論

1. **B1：大語料的關鍵字檢索快了十倍以上，輸出逐題相同。** 154 萬段的企業文件，單獨一題的檢索時間從 42.6 秒降到約 4 秒。Modal 上 470 題整批重跑（判斷用快取），從 8,830 秒降到 143 秒，470 題的檢索名單和原本完全一樣。
2. **B4：EG2 可以在本機入口開了。** `taguri.run` 和 `taguri.query` 加了參數，另有一個建向量的指令。本機用 CPU 載入的 EG2 和雲端建的向量對得上。沒有在本機接真的判官跑過。
3. **B7：能白拿的只有一成多。** 每輪重判 10 段加上證據池 5 段，判斷次數少 11%、輸入 token 少 17%，校準半和檢查半的分數都沒有可量測的差別。再往下省就要拿分數換，砍輪數或砍候選數都會讓「全部找齊的題數」掉 3 到 9 個百分點。
4. 花費約 $4.2，其中約 $1.6 是一次被帳號花費上限中斷、沒有留下結果的執行。

## 1. B1　大語料的關鍵字檢索

### 1.1 時間花在哪

### 1.2 改了什麼

| 原因 | 改法 | 效果 |
|---|---|---|
| 限定範圍的重新計分，SQLite 是一筆 rowid 跑一次查詢，每跑一次 FTS5 都把所有查詢詞的文件頻率重算一遍。154 萬段時每筆 0.125 秒，一次常有上百筆 | 改成掃一次、只替指定的段落計分（SQL 裡把 `rowid IN` 寫成 `+rowid IN`） | 200 筆從 25 秒降到 0.7 秒，分數逐位元相同 |
| 同一個問題的原始查詢，一題裡會重跑 4 次，每次都要替 146 萬個符合的段落計分 | 每個執行緒記住最近幾個查詢的結果 | 每題少 3 次，約省 5 秒 |
| 多個執行緒時，SQLite 每回傳一列就要重新搶一次 Python 的全域鎖 | 段落編號的清單在 SQLite 裡併成一列再回傳 | 4 核機器上開 16 個執行緒，吞吐量從每題 3.1 秒到 1.1 秒 |
| 在 16 核的機器上，16 個執行緒做計分查詢完全沒有比 1 個快（單次 0.54 秒變成 12 秒） | 加一個選項 `--lex-procs N`，把計分查詢交給 N 個工作行程 | 16 核上的吞吐量從每題 4.9 秒到 0.39 秒 |

最後一項的原因沒有查到底，只確定是同一個行程裡的執行緒互相卡住。試過加大 SQLite 的分頁快取和開記憶體映射，都沒有用，所以沒有留在程式裡。

還剩下的固定成本是「替所有符合的段落計分一次」，154 萬段時約 2 到 3 秒。問題很長的時候，幾乎每一段都會符合至少一個詞。這要換成有提前終止的檢索引擎才能再降，SQLite FTS5 做不到。

### 1.5 對 TODO 門檻的判定

門檻是「十萬段以上的語料，詞彙檢索占每題時間的一半以下」。

- 檢索現在是每題約 4 到 5 秒。判官的時間在這個題組每題 168 次判斷、56 萬 token，S10 並行時每題等判官的中位數是 21 秒，而且那一次有一部分判斷是快取。所以檢索占不到一半。**判定：達到。**
- 這個判定用的判官時間是雲端並行時的數字。單獨一題在 GB10 上的判官時間還沒有量（TODO A3）。

### 1.6 用法

- 單題查詢和小語料不用做任何事，修改預設就生效。
- 大語料又同時跑很多題時，加 `--lex-procs N`（`taguri.run`），N 取 CPU 核心數。Modal 的工作設定是 `"lex_procs": 16`。
- 要量自己的索引：`python tools/lexical_profile.py --db <索引> --data-root <資料夾> --dataset <題組> --split <切分> --trace <先前的 trace.jsonl.gz>`。

## 2. B4　EG2 的本機整合

加了三樣東西：

| | 用法 |
|---|---|
| 建向量 | `python -m taguri.dense build --db <索引> --out <向量檔.npy> --model <模型資料夾> --device cuda` |
| 整批評測 | `python -m taguri.run --config N1+EG2 ... --dense-vectors <向量檔> --eg2-model <模型資料夾>` |
| 單題查詢 | `python -m taguri.query ... --dense-vectors <向量檔> --eg2-model <模型資料夾>` |

`--eg2-model` 可以是本機資料夾，不連外網也能用。`--eg2-device` 預設是 `cpu`，查詢的向量在 CPU 上算，GPU 留給判官。EG2 要放在另一個 Python 環境時用 `--eg2-url` 接 `taguri/dense_server.py`。

驗過的範圍（本機 4 核，沒有 GPU）：

| 檢查 | 結果 |
|---|---|
| 本機 CPU 載入的 EG2，替 MuSiQue 前 64 段算向量，和雲端 GPU 建的向量比 | cosine 最小 0.998 |
| 查詢的向量在 CPU 上算一次 | 約 0.07 秒 |
| CPU 上建向量的速度 | 每秒約 14 段（雲端 L40S 是每秒約 550 段）。建向量要用 GPU |
| `taguri.run --config N1+EG2`，判官用看金標的替身，MuSiQue 40 題 | 跑得完。每題平均有 19.9 段是只靠 EG2 進來的 |
| 向量檔的列數和索引不符 | 直接報錯 |
| 沒給向量檔卻用 `N1+EG2` | 直接報錯，訊息裡有建向量的指令 |
| 用雲端 N1＋EG2 那一次的 trace 重放（MuSiQue dev 300 題），本機 CPU 算查詢向量 | 前 10 名和雲端完全相同的有 177 題。對照組（不開 EG2，同樣重放）是 192 題 |

最後一列要說明。重放本身不是精確的：trace 只留每一段的第一次和最後一次判斷，中間的重判沒有留，所以就算不開 EG2 也只有 192 題完全相同。開 EG2 之後是 177 題，在同一個水準。這能說明本機的 EG2 路徑沒有明顯走偏，不能證明和雲端逐題相同。

**沒有驗的**：本機接真的判官（llama-server 或 SGLang）跑 N1＋EG2。這個環境沒有 GPU。企業文件上「加 EG2 追平」的數字是 Modal 入口跑出來的。

另外要帶的套件：`torch`、`torchvision`、`pillow`、`sentence-transformers` ≥ 6.1、`transformers` ≥ 5.19。少了 `torchvision` 模型會載入失敗，雲端和本機都踩過一次。

### 3.3 讀法

- **可以白拿的是 11% 的判斷次數和 17% 的 token。** 這個組合存成 [`thresholds.lite.json`](thresholds.lite.json)，用 `--lock results/thresholds.lite.json` 套用。lock 檔沒有改。
- **再往下，R@5 掉得慢，AE@10 掉得快。** 砍一輪擴展省三成，R@5 只掉 0.5 到 1.7 分，但全部找齊的題目少 3 到 7 個百分點。砍掉的那一輪正好是多跳題走到最後一份文件用的。
- **證據池從 8 段縮到 5 段沒有壞處**，兩批題目的點估計都是正的，區間包含 0。它不省次數，只讓每次判斷短一點。
- 事先定的規則在這裡有擋到東西：r1 在校準半看起來幾乎沒掉分，檢查半上 AE@10 掉了 7.33。
- 這些數字只在 MuSiQue 上量過。段落長的語料（企業文件每題 56 萬 token）上，m5 省的比例會更大，分數的影響沒有量。

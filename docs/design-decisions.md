## 1. 正規化（`taguri/analyze.py`）

1. **逐字元做 NFKC**，不是整串做。理由：要保留「鍵值的每個字元來自原文的哪個位置」。NFKC 已經包含全形轉半形（全形英數、全形標點、全形空白）。代價是跨字元的組合序列不會被合併，對這幾個題組沒有影響。
2. **拉丁字母去掉變音符號**（`Fàbregas` → `fabregas`），只影響鍵值。理由：問題和段落常常一邊有重音符號、一邊沒有。
3. **OpenCC 只轉 CJK 連續片段**。轉換後長度不變就逐字對位；長度變了（詞級對應，例如四個字轉成三個字）用 `difflib` 對齊，對不上的字元歸到該區塊的起點。理由：橋接詞要能還原成原文寫法。
4. 純 ASCII 的文字走快速路徑（只轉小寫），不經過上面的步驟。

## 2. 分欄斷詞

1. **`ids`**：符合 `[a-z0-9][a-z0-9\-_./]{2,}` 而且含數字的字串，去掉結尾的標點後整段保留。**編號裡的英文片段（兩個字母以上）另外放一份到 `latin`**（`covid-19` 的 `covid`）。理由：整段保留才能精確比對編號，但只打前半段的查詢也應該找得到。
2. **`latin`**：轉小寫、去停用詞、Snowball 詞幹。單一 ASCII 字母丟掉。
3. **停用詞表自己寫**：英文約 110 個功能詞（冠詞、代名詞、介系詞、助動詞、疑問詞、連接詞），中文 30 個虛詞。理由：不引入外部詞表，清單短、可檢查。疑問詞（who、what、when）也在裡面，因為它們只出現在問題端。
4. **`cjk_bigram`**：每個 CJK 連續片段切 bigram；單獨一個字的片段保留成 unigram。
5. **`cjk_word`**：jieba 的 search 模式（會同時給長詞和裡面的短詞）。
6. **`title` 欄位放標題的全部鍵值**（四種欄位的 token 混在一起）。理由：標題很短，不值得再分四欄。

## 3. 索引（`taguri/index.py`）

1. FTS5 用 `unicode61` tokenizer，加上 `tokenchars '-_./'`，讓預先斷好的 token（包含帶標點的編號）原樣進索引。
2. **查詢 = 所有查詢鍵值用 OR 串起來**，不指定欄位。FTS5 的 `bm25()` 會把各欄位的詞頻乘上欄位權重後相加，再做一次長度正規化，就是 BM25F 的簡化版。k1、b 用 FTS5 的固定值（1.2、0.75），沒有調。
3. **`title_lookup` 的鍵值**：標題正規化後的表面詞（不取詞幹、保留停用詞、CJK 一字一個 token），用單一空白串起來。標題結尾有括號說明的（`Theodred II (Bishop of Elmham)`），另外存一筆去掉括號的鍵值。
4. **IDF**：`log(1 + (N − df + 0.5) / (df + 0.5))`，df 是「包含這個詞組的段落數」（FTS5 的 phrase 查詢）。

## 4. Q0 錨定

1. 查詢切成表面詞，取 n-gram（英文最多 8 個詞，CJK 最多 15 個字），和 `title_lookup` 完全相符才算命中。從每個起點取最長的命中，再丟掉被更長命中完全包住的。
2. 單一詞的錨定排除停用詞、純數字、單一字元。
3. `ids` 的錨定：查詢裡的編號在 `ids` 欄位完全相符，而且命中段落 ≤ 50 才算（太多代表它不是識別碼）。4 位數以下的純數字（年份）不當編號錨定。
4. 一個錨定對到很多段落時（同一個標題底下有多段），用原查詢的 BM25F 分數取前 5 段。
5. **N0 裡錨定的作用**：命中的段落在 BM25F 分數上加一個固定值（`anchor_bonus`，在校準半上定一次）。理由：N0 沒有判官，只能用分數表達「標題完全相符」這件事。N1 之後錨定命中的段落直接進候選，交給判官。

## 5. Q2 召回與下一輪查詢（Q6）

1. **第一輪**：原查詢的 BM25F 前 50，加上錨定命中的段落。
2. **下一輪查詢 = 原查詢 + 這一輪選中的詞**（不累加前幾輪選過的詞）。理由：每一輪要找的是「下一跳」，前一輪的詞已經把它該找的段落帶進來判過了。
3. **選中的詞加權**：`分數 = bm25(原查詢) + β × bm25(選中的詞)`，β = 2，兩邊各取前 200 段的聯集再算。理由：原查詢通常有十幾個詞，橋接詞只有一兩個，不加權的話新的詞影響不了前 50 名。β 沒有調，用 Rocchio 常見的量級。
4. **取前 50 之後才扣掉判過的段落**（所以擴展輪新判的段落通常少於 50）。理由：照規格的字面意思，而且判斷次數比較少。

## 6. Q3 判證據（`taguri/decide.py`）

1. **題目文字**（英文，寫法 B-L2）：`Does the candidate passage state a fact that helps answer the user question, either directly or as an intermediate step?`，選項 `A. Yes`／`B. No`；使用者的問題在 `[State]` 裡標成 `User question:`。理由：照交接文件的提醒用寬的問法、肯定形。在校準半上比較了 6 種寫法（`taguri/decide.py` 的 `Q3_VARIANTS`，數字在 `results/s6-taguri.md` 第 7 節），選「有已有證據時金標判『是』比例最高」的那一種。最初的寫法（A-L1）太嚴，明顯的第一跳證據也被判否。
2. **prompt 順序**：模板開頭 → `[State]` → 問題 → 已有的證據 → 候選段落 → `[Question]` 與選項。同一輪的所有候選共用到「已有的證據」為止的前綴；有已有證據時先送一筆把前綴放進快取，再整批送。
3. **已有的證據 = 判這一批時的證據池**（最多 8 段，依 log-odds 排序），放全文。
   - **分批判斷**：每一輪的新候選依召回順序每 5 段一批，批與批之間重新算證據池。每段仍然只判一次，沒有違反「不重判」。理由：金標多半在第一輪就被撈到，整批一起判的話全部都沒有上下文。批次大小在校準半上看了「不分批、10、5」，取 5。
   - **錨定命中的段落排在最前面判**。理由：標題完全相符的段落最可能是第一跳，先判才能當後面的上下文。
4. 外框沿用 jevlike v8 的英文寫法（`[State]`、`[Question]`、英文 system 句、最後一句要求只回答字母）。中文版用 jevlike 的 `【狀態】`、`【問題】`，欄位用括號標注（v23）。中文的 system 句改成「你是決策引擎。只回答一個字母。」（原句有「產線」兩個字，和這裡的題目無關）。
5. **跨次執行的判斷結果快取**：以 prompt 全文的 SHA-1 當鍵值，存在 Volume。理由：N1、N1c、N2 第一輪的判斷完全相同，重跑不用再算；同時讓各設定之間的配對比較不受伺服器數值抖動影響。每題的「判斷次數」和「輸入 token」都照**沒有快取**時的數量記（邏輯次數），成本另外用實際容器時間記。

## 7. Q4 證據池

log-odds ≥ τ 的段落依 log-odds 取前 8。同分時依原查詢的 BM25F 分數、再依段落編號。

## 8. Q5 選橋接詞（`taguri/pipeline.py`）

1. **候選來源**：證據池每一段的標題、內文裡的編號（4 位數以下的純數字不算，避免把年份當候選）、內文裡連續的大寫詞組（中間允許 `of`、`de`、`van` 這類連接詞；開頭如果是停用詞就去掉，處理句首的 `The`、`In`）、中文高 IDF 的詞（每段取 12 個）。
2. **排除**：鍵值全部已經在目前為止任何一輪的查詢裡出現過的詞；長度超過 80 字元的詞。
3. **多一道「查了會不會有新東西」的過濾**：用詞組查詢找出包含這個詞的段落，如果全部都已經判過，就不列入候選。理由：這種詞查了也不會帶來新段落，列給判官只是浪費一個選項。這是程式端的準備工作，沒有用到金標。
4. **依 IDF 取前 8 個**，同分時依字母順序。
5. **淘汰賽**：8 個候選依 IDF 名次蛇形分成兩組（第 1、4、5、8 名一組；第 2、3、6、7 名一組），判官每組選 1 個，共選出 2 個、呼叫 2 次。理由：兩組強弱平均；不跨題比較機率（jevlike v19）。候選只有 3 到 4 個時只問一題，取機率最高的 2 個；候選 ≤ 2 個時不問，全部採用。選項順序固定依 IDF 名次。
6. **證據池是空的時候**（沒有任何段落 ≥ τ）：改從 log-odds 最高的 2 段抽候選詞，但 prompt 裡的「已有的證據」仍然是空的。理由：否則第一輪沒過門檻的題目就完全沒有機會擴展。
7. **N1c**：同一份候選清單直接取 IDF 最高的 2 個，不呼叫判官。

## 9. Q7 是否足夠（N2）

每一輪判完之後問一次（證據池是空的就不問，直接繼續）。log-odds > 0 就停。最多 3 輪擴展。門檻固定用 0，沒有調。S6 的結果是 N2 比 N1 差，已拿掉。

## 9b. Q1 題型路由（N3）

1. 題型四選一（單跳／橋接／比較／交集），取機率最高的。
2. 判成比較或交集、而且問題裡錨定到 2 個以上實體時，每個實體（最多 4 個）各跑一條路線：第一輪的召回用「原查詢 + β × 該實體」的加權分數，之後擴展 1 輪；所有路線共用同一個證據池和「已判過」的紀錄。其他情況走一般路線。
3. N2 被拿掉之後，N3 以 N1 為基礎（固定輪數）。第一版把實體文字直接接在查詢後面，因為實體本來就在查詢裡，召回結果完全一樣，等於沒有路由；改成加權後才有差別。

## 9c. Q2b EG2 補充召回（N4）

1. 每一輪用當輪的查詢文字（原問題，或原問題加上選中的詞）取 EG2 前 20 段，扣掉這一輪詞彙召回已有的段落後排在候選的最後面。EG2 的分數不進排序、不進輸出。
2. 文件向量：`title: {標題} | text: {內文}`，最長 512 token，float16，存成 numpy 矩陣，內積暴力比對。
3. EG2 需要比 SGLang image 更新的 Transformers，所以放在同一個容器的獨立 Python 環境（`taguri/dense_server.py`），用本機 HTTP 呼叫。

## 10. Q8 輸出

1. 「同一來源去重」：多跳題組和 MultiHop-RAG 以段落為單位（題組的金標就是段落）；EnterpriseRAG 以文件為單位。
2. 排序方式（`out_mode`）在校準半上二選一後鎖定為 `pool_then_bm25`，見 `results/s6-taguri.md`。
   - `pool_then_bm25`：log-odds ≥ τ 的段落依 log-odds 排，剩下的位置用原查詢的 BM25F 補。
   - `all_logodds`：所有判過的段落都依 log-odds 排，再用 BM25F 補。
3. log-odds 同分時依原查詢的 BM25F 分數、再依段落編號（`handoff/A-to-B.md` §6.1 提醒 log-odds 會有同分）。

## 12. S6 重做的改動（2026-11-10，Clarence 決定重做之後）

第一次 S6 照 §7 的字面做，dev 400 題 R@5 70.54，比 B0 低 11.88 分。重做時改了下面四項，數字在 `results/s6-taguri.md` 第一部分。上面各節裡和這裡不同的地方，以這一節為準。

1. **每輪重判（`rejudge_each` = 20）。偏離 §7.2 Q6「已判過的段落不重判」。** 每一輪判完新段落後，取 log-odds 最高的 20 段；其中「上次判斷時的證據池」和「現在的證據池」不同的，帶著現在的證據池再判一次，新的 log-odds 取代舊的。證據池裡的段落用「其餘的證據池」當上下文。每輪只做一遍（重判後證據池又變了也不再追），最後一輪結束後再做一遍。理由：金標有三分之二在第一輪就被撈到，當時沒有上下文；第二跳的段落要等第一跳找到之後才判得出來。只在最後重判一次不夠（第一次 S6 的診斷只 +2.9 分），因為中間幾輪的證據池和橋接詞也要靠正確的判斷。
2. **暫定證據（`min_pool` = 2）。** 過門檻（log-odds ≥ τ）的段落不足 2 段時，用 log-odds 最高的 2 段當證據池，同時當 prompt 裡的「已有的證據」和橋接詞的來源。取代第 8 節第 6 點（原本只拿來抽候選詞、不放進 prompt）。理由：第一跳的段落常常在沒有上下文時被判否，證據池是空的話整題就沒有東西可以接。
3. **判證據的問法改成 I**：`Does the candidate passage help with the user question? A passage helps if it gives the answer, or if it identifies a person, place, work or thing that the user question describes indirectly.` 取代第 6 節第 1 點的 B。理由：直接告訴判官「指出中間實體」也算；校準半上比 B 高 1.9 分。
4. **輸出排序改成 `all_logodds`**：所有判過的段落都依 log-odds 排，再用 BM25F 補。取代第 10 節第 2 點。理由：重判之後前段的 log-odds 都是帶上下文判的；校準半上比另一種排法高 5.9 分。
5. τ = −6、分批大小 5、候選詞 8 個分兩組、固定 2 輪：沒有變。
6. 試過但沒有採用的：選詞加「都不適合」選項（每組 3 個候選加 1 個「None of these」，選到它就不採用該組）、候選詞優先排「本身是某段標題」的詞、跑 3 輪、重判 30 段、問法 G。程式裡保留了開關（`pick_none`、`term_rank`、`rounds`），預設關閉。

## 13. S7 到 S10 的決定

1. **中文的判證據題目**：直接把英文定案的問法 I 翻成中文（「這個候選段落對回答問題有幫助嗎？（只要段落給出答案，或指出問題裡間接描述的人、地、作品或事物，就算有幫助）」），沒有在中文上另外比較。外框用 `【狀態】`、`【問題】` 和括號標注。
2. **dev-zh 的翻譯**（`tools/translate_musique.py`）：先翻標題建對照表，再翻段落；每段的 prompt 只附「原文裡實際出現的標題」的對照。結尾有括號的標題另加一筆去括號的別名。採用第一次的譯文，理由和第二次失敗的原因在 `results/s7b-dev-zh.md`。
3. **EnterpriseRAG 的分段**（`tools/enterprise_prep.py`）：先在空行切段落，把段落依序併到不超過 2,000 字元；單一段落就超過 2,000 字元時改在換行處切，再不行就在 2,000 字元內最後一個空白處硬切。`title` = 「文件標題 [來源類型]」。題組裡有 4 筆重複的 `doc_id`，保留第一筆。
4. **EnterpriseRAG 的題目**：470 題 = 有 `expected_doc_ids` 而且題型不是 `high_level`、`info_not_found` 的題目。計分以文件為單位：輸出時同一份文件只留排名最前面的段落。
5. **已有證據的 token 預算**：prompt 裡的「已有的證據」從排名最前面開始放，累計超過 10,000 token 就不再放（至少放 1 段）。理由：EnterpriseRAG 的段落接近 2,000 字元，而且多是日誌、程式碼這類 token 密度高的內容，8 段加起來曾經到 17,776 token，超過 16,384 的 context。多跳題組和 MultiHop-RAG 從來沒有碰到這個上限，所以先前各段的結果不受影響。
6. **單題失敗的處理**：某一題在判官呼叫上連續失敗時，該題退回只用詞彙層的排序並在紀錄裡標記，整批繼續跑。失敗題數寫在各次執行的 `summary.json`（`failed_questions`）。
7. **EnterpriseRAG 的 EG2 向量**：分 4 個容器平行建（每個容器只跑 EG2，不跑 SGLang），再合併成一個 float16 矩陣。判官執行時 EG2 和 SGLang 共用一張 L40S，SGLang 的 `--mem-fraction-static` 設 0.72。

## 14. S7 後續：跨語言與中文調整（2026-11-10）

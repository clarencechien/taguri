## 1. 正規化（`engine/analyze.py`）

1. **逐字元做 NFKC**，不是整串做。理由：要保留「鍵值的每個字元來自原文的哪個位置」。NFKC 已經包含全形轉半形（全形英數、全形標點、全形空白）。代價是跨字元的組合序列不會被合併，對這幾個題組沒有影響。
2. **拉丁字母去掉變音符號**（`Fàbregas` → `fabregas`），只影響鍵值。理由：問題和段落常常一邊有重音符號、一邊沒有。
3. **OpenCC 只轉 CJK 連續片段**。轉換後長度不變就逐字對位；長度變了（詞級對應，例如四個字轉成三個字）用 `difflib` 對齊，對不上的字元歸到該區塊的起點。理由：橋接詞要能還原成原文寫法。
4. 純 ASCII 的文字走快速路徑（只轉小寫），不經過上面的步驟。

## 2. 分欄斷詞

1. **`ids`**：符合 `[a-z0-9][a-z0-9\-_./]{2,}` 而且含數字的字串，去掉結尾的標點後整段保留。**編號裡的英文片段（兩個字母以上）另外放一份到 `latin`**（`covid-19` 的 `covid`）。理由：整段保留才能精確比對編號，但只打前半段的查詢也應該找得到。
2. **`latin`**：轉小寫、去停用詞、Snowball 詞幹。單一 ASCII 字母丟掉。
3. **停用詞表自己寫**：英文約 110 個功能詞（冠詞、代名詞、介系詞、助動詞、疑問詞、連接詞），中文 30 個虛詞。理由：不引入外部詞表，清單短、可檢查。疑問詞（who、what、when）也在裡面，因為它們只出現在問題端。
4. **`cjk_bigram`**：每個 CJK 連續片段切 bigram；單獨一個字的片段保留成 unigram。
5. **`cjk_word`**：jieba 的 search 模式（會同時給長詞和裡面的短詞）。
6. **`title` 欄位放標題的全部鍵值**（四種欄位的 token 混在一起）。理由：標題很短，不值得再分四欄。

## 3. 索引（`engine/index.py`）

1. FTS5 用 `unicode61` tokenizer，加上 `tokenchars '-_./'`，讓預先斷好的 token（包含帶標點的編號）原樣進索引。
2. **查詢 = 所有查詢鍵值用 OR 串起來**，不指定欄位。FTS5 的 `bm25()` 會把各欄位的詞頻乘上欄位權重後相加，再做一次長度正規化，就是 BM25F 的簡化版。k1、b 用 FTS5 的固定值（1.2、0.75），沒有調。
3. **`title_lookup` 的鍵值**：標題正規化後的表面詞（不取詞幹、保留停用詞、CJK 一字一個 token），用單一空白串起來。標題結尾有括號說明的（`Theodred II (Bishop of Elmham)`），另外存一筆去掉括號的鍵值。
4. **IDF**：`log(1 + (N − df + 0.5) / (df + 0.5))`，df 是「包含這個詞組的段落數」（FTS5 的 phrase 查詢）。

## 4. Q0 錨定

1. 查詢切成表面詞，取 n-gram（英文最多 8 個詞，CJK 最多 15 個字），和 `title_lookup` 完全相符才算命中。從每個起點取最長的命中，再丟掉被更長命中完全包住的。
2. 單一詞的錨定排除停用詞、純數字、單一字元。
3. `ids` 的錨定：查詢裡的編號在 `ids` 欄位完全相符，而且命中段落 ≤ 50 才算（太多代表它不是識別碼）。4 位數以下的純數字（年份）不當編號錨定。
4. 一個錨定對到很多段落時（同一個標題底下有多段），用原查詢的 BM25F 分數取前 5 段。
5. **N0 裡錨定的作用**：命中的段落在 BM25F 分數上加一個固定值（`anchor_bonus`，在校準半上定一次）。理由：N0 沒有判官，只能用分數表達「標題完全相符」這件事。N1 之後錨定命中的段落直接進候選，交給判官。

## 5. Q2 召回與下一輪查詢（Q6）

1. **第一輪**：原查詢的 BM25F 前 50，加上錨定命中的段落。
2. **下一輪查詢 = 原查詢 + 這一輪選中的詞**（不累加前幾輪選過的詞）。理由：每一輪要找的是「下一跳」，前一輪的詞已經把它該找的段落帶進來判過了。
3. **選中的詞加權**：`分數 = bm25(原查詢) + β × bm25(選中的詞)`，β = 2，兩邊各取前 200 段的聯集再算。理由：原查詢通常有十幾個詞，橋接詞只有一兩個，不加權的話新的詞影響不了前 50 名。β 沒有調，用 Rocchio 常見的量級。
4. **取前 50 之後才扣掉判過的段落**（所以擴展輪新判的段落通常少於 50）。理由：照規格的字面意思，而且判斷次數比較少。

## 6. Q3 判證據（`engine/decide.py`）

1. **題目文字**（英文）：`Does the candidate passage contain information needed for one of the steps in answering the question?`，選項 `A. Yes`／`B. No`。理由：照交接文件的提醒，用寬的問法（「某一步所需的資訊」），不要求段落單獨就能回答；肯定形。
2. **prompt 順序**：模板開頭 → `[State]` → 問題 → 已有的證據 → 候選段落 → `[Question]` 與選項。同一輪的所有候選共用到「已有的證據」為止的前綴；有已有證據時先送一筆把前綴放進快取，再整批送。
3. **已有的證據 = 這一輪開始時的證據池**（最多 8 段，依 log-odds 排序），放全文。
4. 外框沿用 jevlike v8 的英文寫法（`[State]`、`[Question]`、英文 system 句、最後一句要求只回答字母）。中文版用 jevlike 的 `【狀態】`、`【問題】`，欄位用括號標注（v23）。中文的 system 句改成「你是決策引擎。只回答一個字母。」（原句有「產線」兩個字，和這裡的題目無關）。
5. **跨次執行的判斷結果快取**：以 prompt 全文的 SHA-1 當鍵值，存在 Volume。理由：N1、N1c、N2 第一輪的判斷完全相同，重跑不用再算；同時讓各設定之間的配對比較不受伺服器數值抖動影響。每題的「判斷次數」和「輸入 token」都照**沒有快取**時的數量記（邏輯次數），成本另外用實際容器時間記。

## 7. Q4 證據池

log-odds ≥ τ 的段落依 log-odds 取前 8。同分時依原查詢的 BM25F 分數、再依段落編號。

## 8. Q5 選橋接詞（`engine/pipeline.py`）

1. **候選來源**：證據池每一段的標題、內文裡的編號、內文裡連續的大寫詞組（中間允許 `of`、`de`、`van` 這類連接詞；開頭如果是停用詞就去掉，處理句首的 `The`、`In`）、中文高 IDF 的詞（每段取 12 個）。
2. **排除**：鍵值全部已經在目前為止任何一輪的查詢裡出現過的詞；長度超過 80 字元的詞。
3. **多一道「查了會不會有新東西」的過濾**：用詞組查詢找出包含這個詞的段落，如果全部都已經判過，就不列入候選。理由：這種詞查了也不會帶來新段落，列給判官只是浪費一個選項。這是程式端的準備工作，沒有用到金標。
4. **依 IDF 取前 8 個**，同分時依字母順序。
5. **淘汰賽**：8 個候選依 IDF 名次蛇形分成兩組（第 1、4、5、8 名一組；第 2、3、6、7 名一組），判官每組選 1 個，共選出 2 個、呼叫 2 次。理由：兩組強弱平均；不跨題比較機率（jevlike v19）。候選只有 3 到 4 個時只問一題，取機率最高的 2 個；候選 ≤ 2 個時不問，全部採用。選項順序固定依 IDF 名次。
6. **證據池是空的時候**（沒有任何段落 ≥ τ）：改從 log-odds 最高的 2 段抽候選詞，但 prompt 裡的「已有的證據」仍然是空的。理由：否則第一輪沒過門檻的題目就完全沒有機會擴展。
7. **N1c**：同一份候選清單直接取 IDF 最高的 2 個，不呼叫判官。

## 9. Q7 是否足夠（N2）

每一輪判完之後問一次（證據池是空的就不問，直接繼續）。log-odds > 0 就停。最多 3 輪擴展。門檻固定用 0，沒有調。

## 10. Q8 輸出

1. 「同一來源去重」：多跳題組和 MultiHop-RAG 以段落為單位（題組的金標就是段落）；EnterpriseRAG 以文件為單位。
2. 排序方式（`out_mode`）在校準半上二選一後鎖定，見 `results/s6-engine.md`。
   - `pool_then_bm25`：log-odds ≥ τ 的段落依 log-odds 排，剩下的位置用原查詢的 BM25F 補。
   - `all_logodds`：所有判過的段落都依 log-odds 排，再用 BM25F 補。
3. log-odds 同分時依原查詢的 BM25F 分數、再依段落編號（`handoff/A-to-B.md` §6.1 提醒 log-odds 會有同分）。
